PNMS SYSTEM FLOW AND TECHNICAL NOTES
====================================

1) PURPOSE
----------
This document explains:
- Complete backend business flow
- RBAC permission matrix
- Why the architecture is designed this way
- Libraries used and why they are used
- Modules in the codebase and their responsibilities


2) CORE BUSINESS FLOW (END-TO-END)
----------------------------------
FLOW:
Seed -> Sowing -> Germination -> Inventory -> Sale -> Profit

Step-by-step:
1. PlantType (master data) is created by ADMIN.
   - Defines what plant is sold.
   - Stores pricing and lifecycle metadata.

2. Seed batch is created by STAFF.
   - Seeds are consumables (raw material), not sale inventory.
   - Tracks purchased quantity and used quantity.

3. Sowing record is created by STAFF.
   - Consumes seeds from a seed batch.
   - Creates only operational trace (SowingBatch), not stock.

4. Germination is recorded by STAFF.
   - Converts sown seeds into usable plants.
   - Creates PlantInventory batch.
   - This is the first point where stock is created from cultivation.

5. Purchased Inventory can be created by STAFF.
   - For ready plants bought externally.
   - Creates inventory with sourceType=PURCHASED and sourceRef.

6. Sale is created by STAFF.
   - Deducts inventory in FIFO batch order.
   - Captures sale snapshot (price, cost, profit, deductions).

7. Profit report is accessed by ADMIN.
   - Computed from sales, expenses, and labour costs.

Why this flow:
- Prevents fake stock creation from sowing stage.
- Preserves traceability of where stock came from.
- Keeps accounting and inventory consistent.
- Supports auditability and reliable profit reporting.


3) WHY THIS DOMAIN DESIGN
-------------------------
A) Separation of concerns
- PlantType = definition (what)
- Inventory = quantity (how much)
- Seed/Sowing/Germination = production events (how it was produced)
- Sale = stock consumption event

Benefit:
- Avoids coupling catalog with quantity.
- Prevents invalid operations and data drift.

B) Event-driven operational trace
- Sowing and Germination are explicit records.

Benefit:
- Better operational analytics and accountability.

C) Source-based inventory
- sourceType + sourceRef enforce stock origin.

Benefit:
- Every inventory batch is explainable (germinated or purchased).

D) Transactional writes
- Sowing, germination inventory creation, and sales deductions are transactional.

Benefit:
- No partial updates (e.g., sale created but stock not deducted).

E) Snapshot fields in sale
- priceAtSale, costAtSale, profit saved at transaction time.

Benefit:
- Historical reports remain correct even if future prices/costs change.


4) RBAC PERMISSION MATRIX
-------------------------
| Module / Action                                  | ADMIN | STAFF | VIEWER |
| ------------------------------------------------ | ----- | ----- | ------ |
| Auth: Login                                      | Yes   | Yes   | Yes    |
| Users: Create / Update / Disable / View          | Yes   | No    | No     |
| Plant Types: Create / Update / Delete / Image    | Yes   | No    | No     |
| Plant Types: View                                | Yes   | Yes   | Yes    |
| Seeds: Create / Update / Delete / Image          | No    | Yes   | No     |
| Seeds: View                                      | Yes   | Yes   | Yes    |
| Sowing: Create                                   | No    | Yes   | No     |
| Sowing: View                                     | Yes   | Yes   | Yes    |
| Germination: Create                              | No    | Yes   | No     |
| Germination: View                                | Yes   | Yes   | Yes    |
| Inventory: Create (Purchased Inventory)          | No    | Yes   | No     |
| Inventory: View                                  | Yes   | Yes   | Yes    |
| Sales: Create                                    | No    | Yes   | No     |
| Sales: View                                      | Yes   | Yes   | Yes    |
| Customers: Create / Update / Delete              | No    | Yes   | No     |
| Customers: View                                  | Yes   | Yes   | Yes    |
| Expenses: Create / Update / Delete               | No    | Yes   | No     |
| Expenses: View                                   | Yes   | Yes   | Yes    |
| Labours: Create / Update / Delete                | No    | Yes   | No     |
| Labours: View                                    | Yes   | Yes   | Yes    |
| Profit Report: View                              | Yes   | No    | No     |

Why RBAC is designed this way:
- ADMIN controls master/system-level entities.
- STAFF executes operational day-to-day work.
- VIEWER has safe read-only access to avoid accidental mutations.


5) LIBRARIES USED (FROM package.json)
-------------------------------------
A) Runtime dependencies

1. express
- Use case: HTTP server and routing.
- Why used: Standard, lightweight framework for REST APIs.

2. mongoose
- Use case: MongoDB object modeling, schemas, validation, transactions.
- Why used: Enforces data structure, relations, middleware hooks, and session-based writes.

3. joi
- Use case: Request payload validation (body/query/params).
- Why used: Prevents invalid input from entering business logic.

4. jsonwebtoken
- Use case: JWT token generation and verification.
- Why used: Stateless authentication for API calls.

5. bcryptjs
- Use case: Password hashing and comparison.
- Why used: Secure credential storage and login verification.

6. helmet
- Use case: Security headers middleware.
- Why used: Reduces common HTTP security risks.

7. multer
- Use case: Multipart/form-data handling for file uploads.
- Why used: PlantType and Seed image upload endpoints.

8. dotenv
- Use case: Load environment variables from .env
- Why used: Keep secrets/config outside source code.

B) Dev dependency

9. nodemon
- Use case: Auto-restart server on file changes during development.
- Why used: Faster dev feedback loop.


6) INTERNAL MODULES AND WHY THEY EXIST
--------------------------------------
A) app/server/config
- src/app.js: App wiring, middleware, route mounting, error handling.
- src/server.js: Bootstrap/start server.
- src/config/db.js: Database connection setup.

Why:
- Clean separation between app assembly and process startup.

B) models (data layer)
- PlantType.model.js: Plant definition and pricing lifecycle metadata.
- Seed.model.js: Seed batch and usage tracking.
- SowingBatch.model.js: Sowing events.
- Germination.model.js: Germination events and inventory batch linkage.
- PlantInventory.model.js: Sellable stock with source tracking.
- Sale.model.js: Sales transaction + profitability snapshot.
- User.model.js: Authentication and roles.
- Customer.model.js: Buyer records.
- Expense.model.js: Expense ledger.
- Labour.model.js: Labour cost ledger.
- SeedSowing.model.js: legacy/older sowing model reference (if retained).

Why:
- Encodes domain invariants at schema level.

C) routes (transport layer)
- One route file per domain (auth, users, plant-types, seeds, sowing, etc.).

Why:
- Organized endpoint management and middleware composition.

D) controllers (request handlers)
- Parse req/res and delegate business logic to services.

Why:
- Keeps HTTP concerns separate from domain logic.

E) services (business layer)
- Implements operations, validations against DB state, transactions, flow logic.
- Key services include:
  - sowing.service: seed consumption + sowing event
  - germination.service: germination + inventory generation
  - inventory.service: purchased stock creation + FIFO deduction helper
  - sale.service: sale write + inventory deduction + profit fields

Why:
- Central place for complex business logic and reuse.

F) validations
- Joi schemas for each module and endpoint payload.

Why:
- Consistent, declarative request validation.

G) middlewares
- auth.middleware: token verification.
- rbac.middleware: role authorization.
- validate.middleware: Joi validateAsync wrapper.
- errorHandler.middleware: centralized error output.
- upload.middleware: image upload constraints.

Why:
- Cross-cutting concerns are reused consistently.

H) exceptions/enums
- ApiError: operational error class with status codes.
- statusCode enum: central HTTP status constants.

Why:
- Predictable error propagation and response behavior.


7) KEY NON-FUNCTIONAL DECISIONS
-------------------------------
1. Global error handler
- Prevents server crashes and standardizes error responses.

2. Async/await + next(err)
- Ensures runtime errors are propagated correctly in Express.

3. Transactions for critical writes
- Protects data consistency during multi-document updates.

4. Soft delete for seeds/users (where applicable)
- Preserves history while removing active use.

5. Backward compatibility fields/routes retained
- Reduces frontend breakage during incremental migration.
